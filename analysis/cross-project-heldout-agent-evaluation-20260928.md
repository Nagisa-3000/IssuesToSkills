# Cross-project held-out Skill Graph evaluation plan (September 28, 2026)

## Split

The scale-up manifest is `experiments/manifests/cross-project-common-80.json`:
20 shared harness problem families × 4 implementation-bearing Issue/PR cases = 80
cases.  Each family has one case from each of Aider, Hermes Agent, DeepSeek
Harness, and Pi.  The deterministic split generated by
`experiments/make_cross_project_holdout_split.py` holds out the complete
`deepseek-ai/deepseek-harness` project:

- training/catalog: 60 cases, 20 families × 3 projects (Aider, Hermes, Pi);
- held-out transfer test: 20 cases, 20 families × 1 project (DeepSeek);
- no held-out case is sent through Atomic, Workflow, or Pattern extraction;
- the split summary and leakage checks are stored under
  `experiments/manifests/cross-project-common-80-deepseek-holdout/`.

This is deliberately a leave-one-project-out experiment rather than a random
case split.  It measures whether a Pattern/Workflow learned from three agent
harnesses can guide a fresh repository.

## Extraction and graph stages

1. The training cases are extracted from pinned local Git refs with the Codex
   evidence extractor.  The raw run directories remain on `vm-node3` under
   `data/skill-extraction/codex-runs/holdout-train-batch-*`.
2. Only the 60 training episodes are enriched with manifest family metadata and
   passed to bottom-up admission:
   `episode -> Atomic -> Workflow -> Pattern`.
3. The catalog persists SQLite nodes/edges, lifecycle snapshots, BM25 FTS,
   deterministic embeddings, and an HNSW routing index.
4. Held-out cases are represented only by their parent ref, issue-family text,
   target test-file patch, and evaluation metadata.  Their solution refs are
   oracle-only and never enter the graph or agent prompt.

## Test-only task preparation

`experiments/prepare_cross_project_holdout_cases.py` resolves the first parent
of each held-out solution commit, exports that tree into a fresh synthetic Git
repository, and applies only a bounded prioritized set of test/fixture files.
The implementation changes and original Git history are absent.  The visible
test patch is retained so both agents see the same behavioral oracle; an
optional qualification run separately checks that the known solution passes.

## End-task arms

Each held-out case receives two independent fresh `codex exec --ephemeral`
sessions with the same model/provider, timeout, workspace snapshot, and test
commands:

- `no_skill`: issue/family text and visible test paths only;
- `guided`: the same prompt plus BM25/vector/HNSW retrieval, typed graph
  expansion, rendered Atomic/Workflow/Pattern cards, and an LLM applicability
  judgment over only training nodes.

The comparison records success/failure, test results, patch presence, wall
clock, model calls, input/cached/output/reasoning tokens, prompt/context size,
retrieval latency, seed/expanded counts, selected nodes, and leakage gates.

## Feedback and lifecycle

After the training catalog is complete, `run_closed_loop_feedback.py` exercises
retrieval -> LLM judge -> successful use and retrieval -> LLM judge -> failure
review, then persists a revision/quarantine/retirement transition and rebuilds
HNSW.  This is kept separate from the held-out causal task score so lifecycle
mutation cannot leak into the evaluation catalog.

## Interpretation gates

- A held-out task is counted as solved only when the visible focused test
  command(s) pass; setup/dependency failures are reported separately.
- Baseline and guided runs are paired by case and must use separate ephemeral
  sessions; no `resume`/`fork` or prior transcript is allowed.
- Any prompt containing a solution ref, target implementation diff, or target
  repository training node fails the leakage audit.
- Retrieval-level Recall/MRR and Pattern support are descriptive; only paired
  end-task tests establish causal guidance evidence.
- Missing dependencies, unavailable test runners, and non-applicable patterns
  are reported as unavailable rather than silently treated as solved/failed.

## Current verified intermediate results (September 28, 2026)

The lower-cost candidate-admission path has completed on all 60 training cases:

- 311 persisted SkillRecords: 230 Atomic, 72 Workflow, 9 Pattern;
- 299 active records, 576 lifecycle/graph relations, 304 LLM dedup proposals;
- 305 LLM governance calls recorded;
- 9 provisional cross-project Patterns, each currently supported by three
  training Workflows in the persisted Pattern payload;
- 246 Workflow→Atomic references to 219 distinct Atomics (reuse is sparse but
  measurable; repeated references are retained rather than inferred away).

The training-only graph has a SQLite catalog and HNSW index at the corresponding
`admission-runs/holdout-train-preextracted-20260928/` output.  A separate
closed-loop copy verified retrieval→LLM judge→success, retrieval→LLM
judge→failure review, an active revision (`@v2`), and HNSW rebuild with three
LLM calls.  A separate lifecycle smoke verified quarantine→retirement of a
detached skill and a rebuilt HNSW index.

The first 20-case held-out retrieval evaluation (before agent execution) reports
Recall/MRR by arm as follows.  The BM25 and embedding rows are true single
channels; Hybrid fuses both; HNSW is the ANN vector channel; Graph adds typed
expansion and closures.

| arm | Recall@8 | MRR | mean first relevant rank | mean expanded |
| --- | ---: | ---: | ---: | ---: |
| BM25 | 0.65 | 0.642 | 2.54 | 0 |
| Embedding | 0.40 | 0.363 | 5.38 | 0 |
| HNSW | 0.40 | 0.363 | 5.38 | 0 |
| Hybrid | 0.80 | 0.420 | 3.06 | 0 |

These are category-level transfer sanity checks, not end-task success claims.
Graph expansion increases context substantially but worsens this node-level
self-retrieval rank under the current type-priority/top-k policy; the paired
agent results are the causal test.

Oracle qualification has completed for all 20 held-out cases: 17 satisfy the
strict gate that the parent-plus-tests snapshot fails while the known solution
passes. Three large merge/release cases (#4429, #4629, and #4320) remain
unqualified because the selected visible test bundle also fails on the known
solution snapshot; they will remain in the agent matrix with an explicit
`oracle_unqualified` status and will not be pooled into the strict causal
success denominator.
